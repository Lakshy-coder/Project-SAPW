Executive Architecture DecisionThe final system is a sovereign, local-first industrial AI workbench. It is not a generic chatbot and not an LLM-only agent. The system treats language models as untrusted reasoning components and places deterministic tools, validators, security controls, provenance, and cryptographic evidence around them.USER  │  ▼React + TypeScript AI Workbench  │ REST / WebSocket  ▼Node.js + TypeScript API / Orchestrator  │  ├── Auth / RBAC / Sessions  ├── Job & State Manager  ├── Capability Registry  ├── Planner  ├── Model Router  └── Policy / Trust Boundary          │          ▼   Execution Graph / Agent Runtime      ┌──────┼─────────┐      ▼      ▼         ▼    Local   Vision    Reasoning    LLMs    Models     Models      │      │         │      └──────┼─────────┘             ▼      Tool / MCP Gateway       ┌─────┼─────┐       ▼     ▼     ▼     RAG   Calc   Files       │     │     │       └─────┼─────┘             ▼        Verification             │       ┌─────┴─────┐       ▼           ▼   Evidence      Deliverables       │           │       └─────┬─────┘             ▼   Provenance + Signed Audit Receipt             │             ▼      Final Trusted OutputCORE RULENo LLM output becomes a trusted engineering result merely because the model said it. Design Goals and Non-Goals2.1 GoalsOffline-first and air-gap-capable operation with enforceable network boundaries.Industrial task execution: inspection analysis, engineering calculation, SOP/policy retrieval, reasoning/memo generation, and controlled deliverable creation.Specialized local models selected by capability rather than a single-model dependency.Deterministic stateful orchestration with explicit plans, observations, tool calls, validation, retries, and terminal states.Evidence-first answers: every important claim should be traceable to source data, tool output, model invocation, or policy.Tamper-evident and cryptographically verifiable execution records.Secure execution of generated code inside a stronger OS/container boundary.Graceful degradation when a model, document parser, or optional service is unavailable.Professional Word/Excel/PDF/PPTX deliverables suitable for review and approval workflows.Developer-friendly APIs, typed contracts, testability, and modular replacement of models/tools.2.2 Non-goalsDo not claim universal engineering-code compliance unless the exact code edition, formula, assumptions, and validation path are implemented.Do not claim physical air-gapping from application-level socket monitoring alone.Do not call a mutable local file 'immutable' without an external trust anchor or cryptographic signature scheme.Do not silently substitute demo/fallback data for missing user input in a production execution.Do not expose arbitrary code execution or administrative endpoints without a defined security boundary.Do not optimize for maximum model complexity when a deterministic tool is more reliable.3. Deterministic Calculation and VerificationRepresent engineering formulas as versioned deterministic functions, never as prompt-only instructions.Normalize units before calculation; store both original and normalized values.Record assumptions, constants, code edition, formula ID, and input values.Validate ranges and physical plausibility before calculation.Run independent verification where practical: alternate formula implementation, invariant checks, or reference cases.Separate 'calculation succeeded' from 'engineering conclusion approved'.High-risk results require explicit verification status and, where configured, human approval.MODEL SAYS: 7.2 mm       ↓CALCULATOR: required_min = 6.84 mm       ↓VALIDATOR: measured = 7.2 mm >= 6.84 mm       ↓POLICY: within configured acceptance rule       ↓TRUSTED CONCLUSION: PASS13. Secure Code ExecutionThe final sandbox is defense-in-depth. AST filtering remains useful as an early rejection layer, but it is not the security boundary.Run generated code in an isolated container/process namespace.Network disabled by default (network-none).Read-only base filesystem; writable temporary working directory only.Drop unnecessary Linux capabilities; run as non-root.Apply CPU, memory, process-count, file-size and wall-clock limits.Allowlist libraries required for the task.Block host filesystem, Docker socket, device access, credentials and environment secrets.Capture stdout/stderr, exit code, resource usage, and deterministic result metadata.Hash the submitted source and generated result.Reject code that attempts to access prohibited resources before execution.14. Multimodal / Document IntelligenceInput pipeline supports PDF, DOCX, XLSX, TXT, CSV, images and structured metadata.Preserve page/sheet/cell coordinates where possible for evidence.Use OCR only when required; store OCR confidence and source image reference.Vision model output must be structured into typed fields with confidence and source region.Never turn a parser/model failure into a positive inspection result.Missing or ambiguous input must produce BLOCKED / NEEDS_REVIEW, not a silent fixture substitution.Demo fixtures are only available behind an explicit DEMO MODE flag visible in the UI.15. Audit, Provenance and Cryptographic ProofEVENT  ↓canonical JSON  ↓input_hash + output_hash + parent_root  ↓SHA-256 block  ↓append-only audit store  ↓execution root  ↓digital signature  ↓VERIFIABLE EXECUTION RECEIPTEvery meaningful node emits an audit event.Canonicalize JSON before hashing to avoid serialization ambiguity.Hash inputs, outputs, referenced documents, tool versions and artifacts.Chain events through parent hashes.Support multiple parents for graph workflows.Sign the final execution root with a protected private key.Store key metadata and signature algorithm/version.Provide an offline verification command/UI that can validate a receipt without rerunning the job.Distinguish tamper-evidence from tamper-prevention in all documentation.Never expose private signing keys to the application prompt or model.16. Deliverables and Artifact IntegrityGenerate DOCX, XLSX, PDF and PPTX only from versioned templates.Every artifact receives artifact_id, content hash, generator version, template version and execution ID.Artifacts must reference the evidence/citation set used to generate them.Engineering workbooks must preserve formulas/assumptions and include a calculation summary.Approval notes must distinguish AI-assisted drafting from verified facts.Final artifacts are sealed into the audit record.UI must allow the user to compare artifact hash against the execution receipt.17. Coding-Agent RulesSOURCE OF TRUTHCoding agents must treat this document as the architecture contract. They may improve implementation details without violating trust boundaries, schemas, security invariants, or the deterministic-vs-LLM separation.Do not introduce cloud APIs or public inference endpoints into production mode.Do not bypass the orchestrator for privileged tool execution.Do not allow model output to directly write trusted database/audit records without validation.Do not silently fall back to fixture/demo data.Do not expose secrets to LLM context.Do not add an unbounded retry loop.Do not call a retrieval result 'verified' without an independent verification step.Do not label a local hash chain immutable unless a protected trust anchor exists.Do not use application-level monitoring as a substitute for network enforcement.Every new tool requires an input schema, output schema, timeout, permission, risk class, tests, and audit event.Every new model requires capability declaration, resource profile, health check, version and routing policy.Every new artifact type requires content hashing, provenance metadata and verification tests.Every security-sensitive endpoint requires auth, authorization, input validation, rate/size limits where relevant, and audit.All production execution paths must be deterministic where deterministic computation is possible.Prefer explicit typed contracts over loosely structured dictionaries.Keep demo fixtures behind an explicit feature flag and label them in UI and logs.Add tests before or with new security-sensitive behavior.Update architecture documentation when introducing a new trust boundary or external dependency.25. Versioned PoliciesFinal Engineering Principles1 — LLMs ARE REASONERS, NOT AUTHORITIESA model may propose. Deterministic systems decide.2 — RETRIEVAL IS NOT VERIFICATIONA source must be identified, versioned, cited and independently checked when the task requires verification.3 — OBSERVABILITY IS NOT ENFORCEMENTA monitor reports violations; network/container policy prevents them.4 — HASHING IS NOT IMMUTABILITYTamper evidence becomes stronger provenance only when the root is protected by a trust anchor/signature.5 — FAIL CLOSED FOR HIGH-RISK TASKSMissing data, ambiguous evidence, security violations and unverifiable results must never silently become successful conclusions.6 — DEMO RELIABILITY MUST NOT BECOME PRODUCTION DECEPTIONFixtures are allowed only in explicit DEMO MODE and must be visibly labelled.7 — EVERY FINAL ANSWER SHOULD BE EXPLAINABLEThe user should be able to ask: where did this come from, what executed, what verified it, and what exact artifact was produced?8 — BUILD THE PROOF, NOT JUST THE FEATUREThe strongest system is the one that can demonstrate its own correctness, provenance, security posture and execution history.
